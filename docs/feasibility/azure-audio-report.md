## SDK 差异与风险

NAudio 3.3.0 仍提供设计基线指定的 `WasapiCapture` 和 `WasapiLoopbackCapture`，但已把二者标为过时，并推荐 `WasapiRecorderBuilder`。当前实现保留既定 WASAPI 采集类，只对这两处过时警告做局部抑制；未擅自更换采集方案。真实设备兼容性尚无证据。若现场测试暴露问题，应先提交具体错误和复现数据，再决定是否修订设计基线。

Azure Speech SDK 的真实连续识别、三语自动检测、翻译回调顺序和断网恢复均未验证。无数据可支持“延迟达标”或“30 分钟稳定”的结论。

## 补测方法与关卡

1. 安全配置 `AZURE_SPEECH_ENDPOINT`、`AZURE_SPEECH_KEY`；不要将值提交到 Git 或写入报告。
2. 补入 `zh-CN.wav`、`en-US.wav`、`ru-RU.wav` 及各自的许可说明，格式为 16 kHz、16 位、单声道 PCM WAV。
3. 运行 `dotnet test RealTimeTranslation.slnx --filter Category=AzureLive`，再按需以 `RUN_WINDOWS_AUDIO_TESTS=1` 运行 `Category=WindowsAudioManual`。回环测试期间播放项目自有音频，麦克风测试期间人工说话。
4. 用 `dotnet run --project tools/RealTimeTranslation.Feasibility -- --source system --target zh-Hans --duration 00:05:00 --show-text` 等命令执行矩阵；`--show-text` 仅在本地人工核对文本时使用。记录延迟、语言识别、错误类别及资源曲线。
5. 完成混合语言、暂停恢复、断网重试和 30 分钟稳定性实测；将原始测量结果补入本报告。只有系统回环、三语识别、正常网络下多数句子 2～4 秒稳定译文以及 30 分钟稳定性均满足设计要求，才能申请放行 UI 阶段。
