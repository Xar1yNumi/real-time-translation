## 本机真实音频采集

## SDK 差异与风险

NAudio 3.3.0 仍提供设计基线指定的 `WasapiCapture` 和 `WasapiLoopbackCapture`，但已把二者标为过时，并推荐 `WasapiRecorderBuilder`。当前实现保留既定 WASAPI 采集类，只对这两处过时警告做局部抑制；未擅自更换采集方案。当前默认系统回环已完成 30 分钟采集，默认麦克风仅验证 5 秒，其他设备格式仍待测。若现场测试暴露问题，应先提交具体错误和复现数据，再决定是否修订设计基线。

Azure Speech SDK 的真实连续识别、三语自动检测、翻译回调顺序和断网恢复均未验证。无数据可支持“翻译延迟达标”或“Azure 端到端 30 分钟稳定”的结论。

## Azure 实测前置条件与本次尝试

2026-10-30 检查结果：当前进程的 `AZURE_SPEECH_ENDPOINT` 与 `AZURE_SPEECH_KEY` 均未设置；本项目默认的 Windows Credential Manager 目标 `RealTimeTranslation/AzureSpeech` 不存在；仓库中尚无三语语音 WAV。尝试通过应用内浏览器访问 `https://portal.azure.com` 时，应用保存的浏览器权限拒绝了该站点的网络访问，并明确禁止换用其他浏览器、命令或间接方式绕过。没有发起 Azure 请求，也没有创建或读取 Azure 资源密钥。

本次新增的两项离线恢复测试先确认旧实现会停在“重连中”，修复后验证了泛化的 SDK 启动异常重试与旧会话停止异常下的资源清理。它们只证明协调器的本地控制逻辑；真实网络中断、Azure 服务回调与连续翻译仍须在上述前置条件满足后单独测量。

Task 9 的设置窗口已接入“测试连接”流程：只有 Azure SDK 报告会话启动成功后才保存密钥。此判断尚未用真实有效密钥与无效密钥各验证一次；离线假测试不能证明 SDK 在无语音输入时的事件时序或认证结果。字幕窗口接入前，运行时禁用“开始翻译”，避免无字幕及停止入口时上传音频。

## 补测方法与关卡

1. 安全配置 `AZURE_SPEECH_ENDPOINT`、`AZURE_SPEECH_KEY`；不要将值提交到 Git 或写入报告。
2. 补入 `zh-CN.wav`、`en-US.wav`、`ru-RU.wav` 及各自的许可说明，格式为 16 kHz、16 位、单声道 PCM WAV。
3. 运行 `dotnet test RealTimeTranslation.slnx --filter Category=AzureLive`；以 `RUN_WINDOWS_AUDIO_TESTS=1` 重跑 `Category=WindowsAudioManual`。回环测试会自动播放合成音；若需验证麦克风语音，请在其采集期间人工说话并另外核对识别结果。
4. 用 `dotnet run --project tools/RealTimeTranslation.Feasibility -- --source system --target zh-Hans --duration 00:05:00 --show-text` 等命令执行矩阵；`--show-text` 仅在本地人工核对文本时使用。记录语音结束时刻、语言识别、错误类别及资源曲线；30 分钟连续运行时把时长改为 `00:30:00`，检查每分钟译文数是否随持续语音增长。
5. 在有明确测试安排的环境中，分别执行短暂断网和长时间断网，记录 `state-Reconnecting`、`state-Listening` 或 `state-Failed` 的顺序与时间；恢复网络后验证是否仍能产出新的译文，不用仅凭状态变化判定恢复成功。
6. 完成混合语言、暂停恢复、断网重试和 Azure 端到端 30 分钟稳定性实测；将原始测量结果补入本报告。只有系统回环、三语识别、正常网络下多数句子 2～4 秒稳定译文以及 30 分钟端到端稳定性均满足设计要求，才能申请放行 UI 阶段。
