# 中英本地互译与连续字幕设计（2026-11-03）

状态：按项目负责人反馈修订，待确认。

## 目标与范围

按用户提出的 LinguaRelay 方向，先交付 Windows 中英双向实时字幕。用户不再要求翻译期间必须联网；首选本机翻译方案，首次下载并校验所需文件后，断网仍能识别和翻译。保留现有 WPF 悬浮窗、系统声音／麦克风二选一及会话累计记录。首阶段不发布俄语、Azure 或 MyMemory 为默认翻译路径。单应用音源、历史编辑和导出是后续两个独立交付阶段，不能被首阶段的界面承诺为已实现。

“本地模型”对用户的含义是：软件首次下载识别和翻译所需的数据，运行时在本机把声音变成文字、再把文字翻成另一种语言，不需要用户注册或填写密钥。模型由软件管理；最终试用包不要求用户自行安装 Python。

沿用现有的自动源语言识别，只在中文和英语之间判断。用户只选择想看的目标语言“简体中文”或“英语”：识别为另一种语言时翻译；识别为目标语言时显示原文。识别失败或检测到其他语言时不猜测译文。歌曲只是用户随手选取的测试音频，和视频、会议、普通说话使用同一采集、识别与翻译流程，不设歌曲模式，也不把歌曲测试排除在验收外。

## 方案选择

1. **保留 C#／WPF，增加独立本地翻译进程（采用）**：复用现有音频采集、字幕会话与测试；用已验证的本地模型替代联网文本翻译。进程故障边界清晰，但增加 Python/CTranslate2 打包成本。
2. 整体迁移 LinguaRelay：能得到较完整的功能，但要重做当前桌面应用、配置迁移与验收，无法把其已有实测直接视作本项目结果。
3. 纯 .NET 直接推理机器翻译模型：发布形式简单，但编码器／解码器、分词和模型转换需新实现并重新验证，首阶段风险较大。

只借鉴 LinguaRelay 的公开架构与测试方法；不复制其源码。候选翻译模型为 MIT 许可的 `facebook/m2m100_418M`，以 CTranslate2 常驻进程推理中英两个方向。模型和运行库版本、来源、哈希、许可在模型下载任务中固定；模型文件不提交 Git。若同机原型达不到质量、内存与时延要求，不将它接入默认程序，应先报告测试数据再调整模型选择。这里的模型只是技术选择，不增加用户操作步骤。

## 数据流

```text
选定的系统声音或麦克风
  → 现有有界 PCM 队列
  → 经真实语音活动检测的短片段与可替换原文预览
  → 常驻 Whisper 自动识别中文或英语
  → 常驻本地机器翻译进程（只接收定稿原文）
  → 按语句 ID 定稿、追加悬浮历史
```

预览只在本机识别，翻译只处理定稿原文。处理积压时优先丢弃过时预览，保留已入队的最新终稿；音频、文字和历史默认不落盘。翻译进程使用受限长度的逐行 JSON 请求／响应，带请求 ID、方向、文本和错误码；启动超时、崩溃、无效响应和取消均在字幕窗口显示状态，不输出伪译文。一次会话只保留一个常驻模型实例，暂停不释放模型，停止时取消待办并关闭进程。

## 验收门槛

- 用固定许可样本验证中→英、英→中真实识别与译文；中文输出统一简体。测量音频开始到首个原文预览、语句结束到最终译文、冷启动和热运行 P50／P95，记录测试设备。数字先实测再确定是否达到可用标准，不以模型 README 的速度代替本机结果。
- 断开网络后，已有模型仍可开始、暂停、继续并完成两方向翻译；无模型时说明需首次下载，不暗中回退 MyMemory。
- 系统声音、麦克风分别现场验收；连续 10 分钟检查队列上界、内存增长、字幕顺序与重复。测试音频包含普通说话、视频和用户举例的中文歌曲，均走相同流程并记录错字、空输出和伴奏影响；不能只用普通语音的成功结果宣称整个场景已验收。
- 每个任务先写失败测试，再编译、运行相关和全量测试、独立 Git 提交。发布试用包前从解压目录启动，验证模型下载、第三方许可与断网行为。

## 后续阶段

第二阶段增加单应用进程回环，并明确 Windows 版本与受保护音频的限制；第三阶段增加可编辑会话历史和 TXT／SRT 导出。各阶段有独立设计、测试与提交，不拖累首阶段的基础翻译验收。
